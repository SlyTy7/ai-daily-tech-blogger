I covered the 24.22.0 LTS release a few days ago. Its sibling on the Current line, [Node.js 26.12.0](https://nodejs.org/en/blog/release/v26.12.0), is smaller on headline features but has a couple of changes that deserve a closer look, mostly because they sit in places where people usually reach for a dependency.

One caveat up front: the release notes list commit titles and PR numbers, not documentation. Where I describe behavior beyond the title, I'm inferring, and I'll say so.

## http.websocketMask() and websocketUnmask()

The notable-changes section has two `SEMVER-MINOR` entries. The one I find more interesting is `http: add websocketMask() and websocketUnmask()` (#66335, by James M Snell).

Some background on why this matters. In the WebSocket protocol, every frame a client sends to a server is XOR-masked with a 4-byte key. If you've ever written a WebSocket implementation, a proxy, or a test harness, you've written that loop, or you've pulled in a package whose only job is to do it quickly (the `bufferutil` native addon exists largely for this reason).

Having masking exposed on `http` suggests Node core now provides that primitive directly. I haven't seen the API docs, so I can't tell you the exact signatures, whether it operates in place, or how it compares in speed with a native addon. Check the `http` docs for 26.12 before relying on any of that.

Who benefits? Realistically not people using `ws` or a framework's socket layer, since those already handle framing. It's for the people building something lower level:

- A custom WebSocket proxy or gateway that needs to re-mask frames.
- A test client that crafts raw frames to probe a server's edge cases.
- A tool that speaks WebSocket over a socket it already owns.

If you integrate with webhooks and event streams, this is unlikely to change your week. If you write protocol tooling, it removes a dependency decision.

## Permission model fixes

A cluster of commits from Rafael Gonzaga touches the permission model, and they read like the unglamorous work that makes a feature safe to adopt:

- `child_process: propagate config-file permission flags to children` (#66559). If you configure permissions in a config file, spawned child processes now inherit those flags. Without that, a child could be a way around the restrictions you set on the parent, so this closes a gap you'd otherwise have to find the hard way.
- `permission: keep explicit fs grants when dropping a covering directory` (#66556). The title suggests that revoking a broad directory grant no longer wipes out narrower grants you made explicitly inside it.
- `lib: add --allow-fs-vfs to permission available flags` (#66554).
- Documentation updates listing `futimes` among the file-descriptor APIs the permission model disables (#66649).

If you've been waiting to see whether the permission model is something you can put in front of untrusted or semi-trusted code, this is the kind of change log that suggests it's still being hardened. That's a reason to try it, and also a reason not to treat it as a complete sandbox yet.

## Test runner: mock call assertions

In `test_runner`, `add mock call assertions to t.assert` (#66476) is a small quality-of-life change. Today, checking that a mock was called usually means reaching into `mock.calls` and asserting on array lengths and arguments by hand. Assertions on `t.assert` should make those checks read closer to what you mean. Again, I'd confirm the exact method names in the docs rather than guess them here.

Two other test runner commits are worth noting: failing `todo` tests inside suites are now rerun (#66605), and load errors are reported when using `--test-isolation=none` (#66550). The second one matters if you run without isolation for speed, since a module that fails to load is exactly the sort of thing you want surfaced rather than swallowed.

## The rest: dependencies and performance

The dependency bumps include SQLite 3.54.0, acorn 8.19.0, and simdjson 5.0.3, along with a pair of V8 cherry-picks. There are also several crypto commits (#66413) removing key locking in places like RSA-OAEP, KEM, and verify setup, and `http: reduce raw header name allocations` (#66488). The notes don't include benchmark numbers, so I can't say how much any of this helps. If you run header-heavy or crypto-heavy services, it's worth profiling before and after.

## The security release is the real deadline

None of the above is what I'd prioritize this week. The Node.js project has announced [security releases for the 26.x, 24.x, and 22.x lines](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases) on or shortly after October 21, with a highest severity of HIGH. The announcement doesn't describe the vulnerabilities, and it notes that End-of-Life versions are always affected.

So the practical plan is simple. Don't spend the next day upgrading to 26.12.0 for WebSocket masking. Work out which Node versions your services and CI images run, make sure none of them are EOL, and be ready to roll the patched releases as soon as they land. Then come back and try the new APIs on a branch.

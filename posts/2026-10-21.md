Node.js put out a coordinated [security release](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases) today: [26.12.1](https://nodejs.org/en/blog/release/v26.12.1), [24.22.1](https://nodejs.org/en/blog/release/v24.22.1) and [22.23.4](https://nodejs.org/en/blog/release/v22.23.4). The advisory lists ten CVEs. The page gives no mitigations; the guidance is simply to upgrade your line.

This is less a "read the changelog" post and more a "go check your fleet" post. Patch releases like this tend to sit unapplied because the version baked into a Dockerfile, a serverless runtime setting, or a CI image is nobody's job. So here's a small way to make it somebody's job.

## What's in it

From the advisory, the High-severity items are:

- **CVE-2026-105482:** `dns.resolve` truncates names containing a NUL character.
- **CVE-2026-105483:** the TLS certificate hostname check can be bypassed when an IP is written with fullwidth digits.
- **CVE-2026-106069:** a related TLS hostname-check bypass when the host loosely resolves to an IP address.
- **CVE-2026-111497:** an out-of-bounds write in the Brotli decoder that the advisory says permits remote code execution.

Medium and Low items cover an HTTP keep-alive socket handling a response written before the request was sent, non-canonical IPv4 hostnames letting DNS SANs authenticate IP endpoints, `crypto.randomUUID()`/`randomInt()` caches being saved into startup snapshots and single executable applications (so every process repeats the same values), and a few Permission Model issues (a `fs.realpathSync` bypass and a wildcard over-grant). Dependency bumps ride along too: c-ares, OpenSSL (24.x and 22.x), SQLite (22.x), Undici, and a CA certificate change.

Two things jump out for the kind of work I do:

1. **Anything that calls out over TLS or fetches compressed responses is in scope.** That's every webhook receiver, every CRM API client, every LLM SDK. The TLS hostname bugs affect outbound verification, and Brotli decoding happens quietly when a server sends `Content-Encoding: br`.
2. **The snapshot/SEA entropy bug is easy to miss.** If you ship a single executable application or use startup snapshots, rebuild it. Upgrading the Node binary on the box doesn't fix an artifact you already built.

The 24.22.1 notes also say several fixes were developed in the private `node-private` repo, so the release notes don't carry every detail. Treat the advisory as the source of truth and don't try to infer more.

## Step 1: know what you're running

Fixed versions per line, from the advisory: 26.12.1, 24.22.1, 22.23.4. A tiny script that fails when the running Node is behind:

```js
// scripts/check-node-patch.mjs
const MIN = { 26: [26, 12, 1], 24: [24, 22, 1], 22: [22, 23, 4] };

const cur = process.versions.node.split(".").map(Number);
const min = MIN[cur[0]];

if (!min) {
  console.error(`Node ${process.versions.node}: no patched release tracked for this line. Move to 22, 24 or 26.`);
  process.exit(1);
}

const behind = cur.some((n, i) => {
  // first differing segment decides
  return cur.slice(0, i).every((v, j) => v === min[j]) && n < min[i];
});

if (behind) {
  console.error(`Node ${process.versions.node} is below ${min.join(".")}. Upgrade.`);
  process.exit(1);
}
console.log(`Node ${process.versions.node} OK`);
```

Run it as a `preinstall` or a CI step. I like it in CI because it checks the runtime the job actually uses, not the one a README claims.

Note the end-of-life warning in the advisory: unsupported lines are affected by these issues too, and the page points to the release schedule. If your script prints the "no patched release" branch, that's a migration ticket, not a patch ticket.

## Step 2: find the places the version hides

Grep for the usual suspects:

```bash
grep -rnE "node:[0-9]+|FROM node|nodejs[_-]version|\"node\":|runtime:" \
  Dockerfile* .nvmrc .node-version package.json .github/ serverless.* 2>/dev/null
```

Pinned image tags like `node:24.22.0-slim` need a bump to `24.22.1`. Floating tags like `node:24` still need a rebuild with the cache busted, or you keep the old layer. Managed runtimes (serverless platforms, hosting providers) are the ones to confirm separately: check their own changelog for when the patched version lands rather than assuming.

## Step 3: rebuild artifacts, then verify

- Rebuild container images and redeploy.
- Rebuild any SEA or snapshot-based binaries (see the entropy issue above).
- After deploy, hit a health endpoint that returns `process.version` so you can confirm in production, not just in the pipeline.

```js
app.get("/healthz", (_req, res) => {
  res.json({ ok: true, node: process.version });
});
```

Exposing the exact runtime version publicly isn't free, though. Put it behind auth or an internal route if the service is internet-facing.

## Takeaway

The upgrade itself is a one-line version bump. The real work is knowing every place that line lives. A fifteen-line CI check turns "did we patch?" from a memory test into a red build, and that's worth having before the next advisory, not after.

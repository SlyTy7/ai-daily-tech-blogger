The Nov 11 security releases (26.13.1, 24.22.3 and 22.23.5) are out, and the notes are a long list of HTTP/2 and TLS fixes, many of them rated High. I'm not going to re-walk the CVE list. The more useful question for most teams is boring: how do you know every place you run Node is actually on a patched version, and stays there?

Version drift is the usual failure. A Dockerfile pins `node:24`, a CI image caches an old layer, a serverless runtime upgrades on its own schedule, and someone's laptop is on whatever `nvm` last installed. A patch you applied in one place tells you nothing about the others.

## What the releases give you

Each LTS line has a specific fixed version, per the release notes:

- [Node.js 26.13.1 (LTS)](https://nodejs.org/en/blog/release/v26.13.1)
- [Node.js 24.22.3 (LTS)](https://nodejs.org/en/blog/release/v24.22.3)
- [Node.js 22.23.5 (LTS)](https://nodejs.org/en/blog/release/v22.23.5)

All three are labelled security releases. The High-rated entries include several in `http2` (headers released when a stream is removed, streams abandoned by nghttp2, buffers and streams retained during pending writes) and in `tls` (nested parser execution from empty writes, resumption and SNI handling). One thing I noticed while reading: the 26.x and 24.x notes list a fix for a remotely reachable TLS server crash that I didn't see in the 22.x notable changes. Don't read anything into that without checking the full changelog; it may just be how the notes are grouped.

The point for this post is simpler: for each major line, there is a floor, and anything below it is behind.

## The guard

A small script that compares `process.version` to a table of minimum versions per major:

```js
// scripts/check-node-version.js
const MIN = {
  22: [22, 23, 5],
  24: [24, 22, 3],
  26: [26, 13, 1],
};

const [major, minor, patch] = process.versions.node.split(".").map(Number);
const floor = MIN[major];

if (!floor) {
  console.error(`Node ${process.version}: no patched floor known for v${major}.`);
  process.exit(1);
}

const current = [major, minor, patch];
const behind = current.some((n, i) => {
  // first differing segment decides
  return current.slice(0, i).every((v, j) => v === floor[j]) && n < floor[i];
});

if (behind) {
  console.error(`Node ${process.version} is below ${floor.join(".")}. Upgrade.`);
  process.exit(1);
}
console.log(`Node ${process.version} OK`);
```

Two decisions in there are deliberate. First, an unknown major fails instead of passing, so an EOL line like 20 or an odd-numbered release doesn't slip through silently. Second, the table is data, so the next security release is a one-line change.

## Where to run it

- **CI**, as the first step, so a stale cached image fails fast instead of shipping.
- **Container startup**, as a `node scripts/check-node-version.js && node server.js` entrypoint, if you want the check at the place that matters (the deployed runtime). For a long-lived service I'd rather have it log loudly than refuse to boot, so make that call per service.
- **`engines` in package.json**: `"engines": { "node": ">=24.22.3" }` with `engine-strict=true` in `.npmrc` covers installs, but it's a single range and doesn't express a per-major floor, which is why I prefer the script.

## The caveat

This only checks the version of the runtime that executes the script. It can't see the other containers, the Lambda layer, or the box under someone's desk. Treat it as a tripwire on the paths you control, and pair it with whatever inventory you already have for the rest.

The check also says nothing about whether you were exposed in the first place. If you don't run an HTTP/2 or TLS server on Node, the practical risk is different from a public-facing service that does. Reading the notes against your own architecture is still the human part.

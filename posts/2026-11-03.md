Most patch releases get a skim and an upgrade. [Node.js 24.22.2](https://nodejs.org/en/blog/release/v24.22.2) (the 'Krypton' LTS line, dated 2026-10-28) deserves a slightly slower read, because one entry in a short changelog is more interesting than it looks.

## What's in the release

The commit list is small: four V8 backports and cherry-picks under `deps`, and one change in `stream`:

> stream: keep async context of parked writes (Matteo Collina) #66907

That's it. No security advisory in the notes, no new API. The V8 items are the usual maintenance, and I can't tell you much about them from the changelog alone beyond the commit hashes and PR numbers, so I won't pretend to.

## Why the stream commit is the one to look at

The release notes only give the one-line title, so what follows is my reading of it, not a summary of the PR. "Parked writes" most plausibly means writes that a stream accepted but couldn't flush immediately, the ones that sit in the buffer when backpressure kicks in. "Keep async context" most plausibly refers to the context that `AsyncLocalStorage` and related async-hooks machinery propagate across callbacks.

If that reading is right, the failure mode is easy to picture. You have a request handler that sets a request ID in an `AsyncLocalStorage` store. The handler writes to a stream, the stream is under backpressure, and the write is parked. When the write's callback eventually fires, the callback runs in the wrong async context, or none. Anything you do in that callback, such as logging "response flushed" with the request ID, loses the ID or picks up someone else's.

That's a bad kind of bug: it doesn't crash, it just makes your traces subtly wrong, and only under load, because only then do writes actually park.

I'd check the PR before leaning on this. If you want to know whether you were affected, the thing to test is a slow consumer: write more than the high-water mark to a stream, read slowly on the other end, and compare the `AsyncLocalStorage` store seen in the write callback with the one set at call time.

```js
import { AsyncLocalStorage } from 'node:async_hooks';
import { Writable } from 'node:stream';

const als = new AsyncLocalStorage();

const slow = new Writable({
  highWaterMark: 4,
  write(chunk, _enc, cb) {
    setTimeout(cb, 50); // slow consumer forces later writes to park
  },
});

for (const id of ['a', 'b', 'c']) {
  als.run(id, () => {
    slow.write('12345678', () => {
      console.log('flushed, expected', id, 'got', als.getStore());
    });
  });
}
```

I haven't run this against 24.22.1 versus 24.22.2, so treat it as a starting point for a repro rather than proof of the bug. If the two lines disagree on the older version and agree on the newer one, you've found what the commit fixes.

## What I'd do with it

- **If you run Node 24 LTS in production**, take the patch. It's low-risk by the look of the changelog, and the stream change is a correctness fix.
- **If you use `AsyncLocalStorage` for request-scoped logging or tracing** (common in HubSpot webhook receivers and serverless handlers, where correlating a webhook delivery to its downstream CRM API calls is half the debugging), run the repro above on your current version. Missing request IDs on "flushed" or "finished" log lines under load are a plausible symptom.
- **Don't expect a headline.** Fixes like this rarely get one, which is the argument for reading patch changelogs rather than only the minor-version ones.

## And the other LTS release that day

[Node.js 26.13.0](https://nodejs.org/en/blog/release/v26.13.0) landed the same day and is the transition of 26.x into LTS under the codename 'Lithium', supported through the end of April 2029. By the notes, it contains no changes from 26.12.1 beyond metadata such as the `process.release` object. One practical note from the release text: since Node 25, the official Linux binaries are linked against `libatomic`, which you may need to install separately if you're coming from Node 24 or earlier. That's worth knowing before you bake a new base image and find the binary won't start.

So the two releases are a nice contrast. One is a big-sounding milestone that changes essentially nothing in the code; the other is a quiet patch with a fix that could change what your logs say. I'd rather have the second kind of surprise.

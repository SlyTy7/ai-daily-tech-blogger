Node has posted its [pre-announcement for the November 11 security release](https://nodejs.org/en/blog/vulnerability/november-2026-security-releases). It's thin on purpose: new versions of the 26.x, 24.x and 22.x lines "on or shortly after" Wednesday, November 11, and the highest severity fixed in each of those lines is HIGH. No CVE details yet. End-of-Life lines are always affected by releases like this, so if anything of yours is still on 20 or older, that's the real finding.

You can't patch what isn't published, but you can make the patch day boring. The useful prep is knowing, in one command, which of your services run which Node, and having a gate that fails loudly when one is below the fixed version.

## Step 1: inventory what you actually run

Don't trust `.nvmrc`. Check the runtime. A tiny endpoint or startup log line is enough:

```js
// log-runtime.js
console.log(JSON.stringify({
  node: process.version,
  release: process.release.lts ?? null, // LTS codename, undefined on Current
}));
```

For HubSpot-style serverless functions or webhook receivers where you don't control the runtime directly, check the platform's runtime setting instead, and note it somewhere searchable. The point is to end up with a list: service, Node line, where the version is set.

## Step 2: add a minimum-version gate

Once the advisory is published, you'll have the patched version for your line. Until then, this script takes a table you fill in later. Empty entries mean "not announced yet" and the script only warns.

```js
// check-node.js
const MIN = {
  22: process.env.MIN_NODE_22 ?? null, // fill in after Nov 11
  24: process.env.MIN_NODE_24 ?? null,
  26: process.env.MIN_NODE_26 ?? null,
};

const cmp = (a, b) => {
  const [x, y] = [a, b].map((v) => v.replace(/^v/, "").split(".").map(Number));
  for (let i = 0; i < 3; i++) if (x[i] !== y[i]) return x[i] - y[i];
  return 0;
};

const major = Number(process.versions.node.split(".")[0]);
const min = MIN[major];

if (!(major in MIN)) {
  console.error(`Node ${process.version} is not in a line covered by this release (or is EOL).`);
  process.exit(1);
}
if (!min) {
  console.warn(`No patched version set for ${major}.x yet; running ${process.version}.`);
  process.exit(0);
}
if (cmp(process.version, min) < 0) {
  console.error(`Node ${process.version} < ${min}. Upgrade before deploying.`);
  process.exit(1);
}
console.log(`Node ${process.version} OK (>= ${min}).`);
```

Wire it into CI and your container entrypoint:

```bash
node check-node.js && node server.js
```

On November 11 the whole job becomes setting three environment variables from the advisory. No hunting through repos.

## Step 3: know which line you're moving to

If you're still deciding between lines, the [26.13.0 release notes](https://nodejs.org/en/blog/release/v26.13.0) matter. That release is the transition of 26.x into LTS (codename "Lithium"), with support through the end of April 2029. According to the notes, it contains no changes from 26.12.1 beyond metadata such as the `process.release` object, so it's a low-risk bump if you were already on 26.12.x.

One detail to check when jumping from 24 or 22: the same notes say that since Node.js 25, the official Linux binaries are linked against `libatomic`, which may need installing separately depending on your distro. In a slim container image, that's the kind of thing that fails at startup rather than in review. Test your base image now, while nothing is on fire.

## A short checklist

- List every service and its Node line today.
- Move anything on an EOL line first; it gets no fix.
- Build and boot your images on 26.13.0 in a branch, `libatomic` included.
- Add the version gate and leave the minimums blank.
- On release day, read the advisory, fill the three values, deploy.

I'd rather spend an hour on this now than discover during a HIGH-severity patch window that one forgotten webhook worker was pinned to an old image.

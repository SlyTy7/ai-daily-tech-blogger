If you only do one thing from last week's news, make it the Node upgrade. The rest of this is why, and what else is worth a glance.

## 1. The November 11 security release

Node published [security releases for the 26.x, 24.x and 22.x lines](https://nodejs.org/en/blog/vulnerability/november-2026-security-releases): [26.13.1](https://nodejs.org/en/blog/release/v26.13.1), [24.22.3](https://nodejs.org/en/blog/release/v24.22.3) and [22.23.5](https://nodejs.org/en/blog/release/v22.23.5). The release notes list a pile of fixes rated High, Medium and Low, and the High ones cluster around HTTP/2 and TLS. A few stand out for anyone running a plain `http2` or `https` server.

**HTTP/2 remote abort (CVE-2026-123863).** According to the advisory, an unauthenticated client can crash a server by getting an `Http2Stream` that still holds nghttp2-allocated header buffers to outlive its session. That trips a `CHECK_EQ` assertion during session teardown and kills the process. The trigger is a default `http2` server whose handler responds before the request body has ended, which the advisory calls typical. It's described as a variant of CVE-2024-27983 that the earlier fix missed. The earlier fix only detached streams still tracked in the session.

**HTTP/2 session leak (CVE-2026-123865).** A peer that triggers a protocol error (the advisory's example is an oversized frame header) while a session is already shutting down can leave a dangling session. The advisory says that leaks memory and file descriptors permanently. No crash needed, so it's the kind of thing that shows up weeks later as a slow memory climb.

**The one I'd read twice: HTTPS and a zero-length write (CVE-2026-123864).** This is a re-entrancy bug. The advisory says `TLSWrap::DoWrite()` calls `ClearOut()` directly for a zero-byte write. If that write is issued from JavaScript running inside the HTTP parser's `on_body` callback, the next TLS record gets decrypted while the parser is still mid-body, and `llhttp_execute()` is re-entered. The result is a use-after-free and an out-of-bounds heap read, and the advisory says it can expose other connections' data, including TLS private keys.

The conditions are narrow. A handler has to call `res.flushHeaders()` before the request body ends and later call `res.end()` with a non-empty chunk, and some ordinary route has to echo or store the request body for the attacker to read anything. The advisory also says cleartext `node:http` isn't affected. Narrow isn't the same as rare, though. "Flush headers early, write a body later" is a normal streaming pattern, so grep your handlers rather than assuming you're fine.

Beyond those three, the release notes list more High items in `http2` (stream and buffer lifetime during pending writes) and `tls` (a remotely reachable server crash, plus a set of changes around resumption and SNI), along with Medium fixes like redacting proxy credentials in invalid proxy URL errors. I haven't dug into those individually, so read the advisory for specifics before you triage.

### What to do

- Upgrade to 26.13.1, 24.22.3 or 22.23.5, depending on your line. The advisory lists only 24.x and 26.x as affected by the first HTTP/2 abort, but 22.x is listed for the HTTPS issue, and the 22.23.5 notes carry several HTTP/2 fixes, so it still needs the update.
- Check the release notes for your line, since the 22.x release lists fewer items than 24.x and 26.x.
- If you can't deploy today, an HTTP/2 front end that terminates TLS and speaks something simpler to Node is a reasonable stopgap. I'm inferring that from the bug descriptions, not from any official guidance.
- The releases also bump dependencies: llhttp 9.4.4, sqlite 3.54.1, and undici (8.12.4 on 26.x, 7.30.2 on 24.x). Note that if you pin undici yourself, your pin doesn't pick up the bundled fix.

## 2. Node 27 alpha, briefly

A day later, [27.0.0-alpha.0.1.0](https://nodejs.org/en/blog/release/v27.0.0-alpha.0.1.0) went out. It's an alpha, so treat it as a preview of direction, not something to run. The notable-changes list is short:

- `child_process`: a new `subprocess.timedOut` property.
- `crypto`: X.509 generation with CSR support, plus more explicit inspection guards.
- `dns`: identical concurrent `lookup()` requests get coalesced.
- `http`: body spans are batched per parser execute.
- `sea`: a compile cache for the VFS modules.
- `worker`: streams are preloaded into the startup snapshot.

Two of those read as quality-of-life. `subprocess.timedOut` removes the little flag people currently track by hand when they kill a child on a timeout. DNS lookup coalescing is the kind of change that quietly cuts duplicate work under load, though I'd want to see the semantics before relying on it, for instance how errors propagate to the merged callers.

The `http` change interests me for a different reason. It touches the same parser path that the TLS bug above lives in. I'm not suggesting the two are related, since the notes don't say so. It's just a reminder that this part of Node is under active change, so test your streaming handlers when 27 gets closer.

## The short version

Patch this week. Search your servers for early `flushHeaders()` followed by a late `end(chunk)`. Leave the 27 alpha alone until it's further along.
